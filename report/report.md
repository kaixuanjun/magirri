# Magic-Log → LogC3 实时映射管线：桌面参考实现与量化验证报告

> 生成命令：`python -m magicrri verify --out report`  
> 版本：magicrri 0.1.0　numpy 2.5.4  
> **所有 LUT 均为合成替身**（没有荣耀 / ARRI 的原始 `.cube`）。本报告验证的是**实现的正确性与数值边界**，不是对 ARRI 色彩的保真度。

## 0. 结论摘要

1. **管线数值闭环成立。** 24 色块端到端 ΔE2000 均值 **0.31**、中位 0.15、P95 0.84、最大 2.86（最差色块：blue 蓝）；肤色均值 **0.13**，灰阶均值 0.19。指导书 §4 的门槛是「中间调均值 < 5、肤色 < 4」，**两项均通过**。需要注意：这是**自洽闭环**下的数字（合成 LUT 由同一套数学生成），它证明实现没错，不证明结果像 ARRI。

2. **三个最容易翻车的点，代价已被量化。** 遗漏 Rec.709 OETF 逆 → 平均 ΔE **14.33**；用 gamma 2.4 顶替 → **5.95**；跳过 709→AWG3 → **8.00**，且饱和度整体偏 **11.6%**。

3. **宽容度损失是硬边界，不是调参能补的。** 管线最高只能到 LogC3 码值 0.5706（线性 1.0），而原生 LogC3 在码值 1.0 处对应线性 55.1（8.26 档）。**顶部实际损失 5.76 档**；18% 灰以上只剩 2.50 档可用（实测饱和点 +2.5 档，理论值 +2.47 档）。

4. **10-bit 是底线这条判断成立。** 有效输入域内，10-bit 输入得到 482 个不同的 10-bit 输出码值、平均步长 2.06 码、最大空档 4 码；换成 8-bit 输入后输出码值掉到 126 个、平均步长 7.93 码，相邻输出码值之间最大 ΔE 达 **0.92**（10-bit 为 0.28）——这就是渐变区会出现台阶的直接量度。

5. **LUT 顺序（R 变化最快）写反 = R/B 通道互换。** 还原 LUT 读反后 ΔE **20.77**，Look LUT 读反后 ΔE **21.64**。两者都不是噪点或条纹，而是**系统性的品红/黄绿偏色**——它看起来「像某种色彩风格」，极容易被误判成「LUT 本身就这样」而放过。这就是必须用回归测试钉死顺序的原因。

6. **指导书 §3.2 的填充顺序写反了。** 规范与主流实现都是「红色变化最快」，本条已在代码中按规范实现，并用官方最小示例做了回归测试（`tests/test_color_cube.py::test_order_is_red_fastest`）。

7. **最关键的工程前提不成立：第三方 App 拿不到 Magic-Log。** Magic-Log 是荣耀相机 App 内部的视频模式，Camera2 只暴露 RAW/YUV，不会给你那条厂商 Log 曲线。详见 §9。

## 2. E0 数学自检

| 量 | 值 | 说明 |
|---|---|---|
| LogC3 分段点（线性/码值） | 0.010591 / 0.149658 | 两段曲线在此拼接 |
| 分段处跳变 | 2.50e-07 | 公开常数自带的舍入误差 |
| 编码→解码往返最大误差 | 4.77e-07 | float32 下的实现误差 |
| 709 OETF→逆往返最大误差 | 1.79e-07 | 同上 |
| 709 分段跳变 | 2.49e-04 | 标准常数 (1.099,0.099,0.45) 在 0.018 处本就不连续（约 0.26 个 10-bit 码值），不是 bug |
| 线性 0.18 → 码值 | 0.3910 | ARRI 惯例的 0.391 |
| 线性 1.0 → 码值 | 0.5706 | 管线输出的上限 |
| 码值 1.0 → 线性 | 55.08 | 原生 LogC3 的顶部余量 |
| 18% 灰到码值 1.0 | 8.26 档 | 原生 LogC3 的标称上限 |

**色域矩阵。** 由基色色度坐标推导（不是抄数），行和 = 1.000000000000, 1.000000000000, 1.000000000000（白点守恒），推导逆对往返误差 1.11e-16。

另有一组常被引用的 AWG3→709 矩阵，与推导结果最大相差 **0.5792**。反解该矩阵隐含的基色可得 B 基色色度 (0.0861, -0.102)——一个「虚基色」，说明它要么不是纯基色变换（含厂商自有的渲染矩阵），要么转录有误。**本实现以可复算的推导矩阵为准，并在 E2 里量化了换用它的代价**（ΔE 8.89）。正式项目必须用 ARRI 官方文档或 OCIO 配置核对这一步，不能靠记忆抄数。


**一个必须知道的结论：AWG3 并不包含 Rec.709。** 把 709 的三个基色送进 709→AWG3 矩阵，得到：

| 709 基色 | 在 AWG3 中的坐标 (R,G,B) | 是否越界 |
|---|---|---|
| R | (+0.595, +0.053, +0.013) | 在界内 |
| G | (+0.213, +1.330, +0.018) | 在界内 |
| B | (+0.193, -0.383, +0.969) | 越界 |

纯 709 蓝在 AWG3 里是 (+0.193, -0.383, +0.969)——**绿通道深度为负**。也就是说 AWG3 的红、绿两角比 709 更宽，但**蓝角比 709 更靠内**（AWG3 蓝基色 y=0.154，709 蓝基色 y=0.060）。指导书 §2.4 的「AWG3 比 Rec.709 更宽」只对红/绿成立。
后果是：`linear_awg3` 出现负值 → LogC3 编码后落在 LUT 定义域之外 → 被钳到 0 → **高饱和蓝/青被降饱和**。这就是 E1 里最差色块是 blue（ΔE 2.86）的原因；它属于路线自带的色域裁切，不是实现错误。

如果这一点不可接受，有两条出路：(1) 换用蓝基色更靠外的色域与对应 Log（例如 ARRI 后续的 AWG4/LogC4，或直接以 ACES AP1 为工作空间），代价是整套曲线参数要换；(2) 在 LogC3 编码之后、LUT 之前插入一个「负值压平」的软钳位，把裁切改成渐变，避免硬拐点带来的色相跳变。

## 4. E2 消融与灵敏度

每个变体与基线在同一输入上对比。「对基线 ΔE」= 该变体输出与基线输出的逐色块 ΔE；「对参考 ΔE」= 与 ColorChecker 参考的 ΔE。

| 变体 | 对基线 ΔE 均 | 对基线 ΔE 最大 | 对参考 ΔE 均 | 最大码值差 | 彩度比 |
|---|---|---|---|---|---|
| 基线（正确配置） | 0.00 | 0.00 | 0.31 | 0.000 | 1.000 |
| 遗漏 Rec.709 OETF 逆 | 14.33 | 22.38 | 14.47 | 0.253 | 0.760 |
| 用 gamma 2.4 代替 OETF 逆 | 5.95 | 8.63 | 5.92 | 0.127 | 1.110 |
| 跳过 Rec.709 → AWG3 基色变换 | 8.00 | 19.32 | 8.16 | 0.400 | 1.116 |
| 三线性插值（33³） | 0.22 | 0.76 | 0.46 | 0.010 | 1.003 |
| 65³ LUT + 四面体 | 0.17 | 0.88 | 0.15 | 0.058 | 1.000 |
| 解析式还原（不查表） | 0.09 | 0.56 | 0.25 | 0.012 | 0.999 |
| 输入 8-bit 量化 | 0.35 | 1.21 | 0.48 | 0.006 | 0.997 |
| 还原 LUT 的 R/B 轴读反 | 20.77 | 52.59 | 20.77 | 0.785 | 0.934 |
| ARRI LUT 的 R/B 轴读反 | 21.64 | 48.72 | 21.64 | 0.906 | 0.968 |
| 用 v1 还原 LUT 处理 v2 素材 | 2.03 | 2.44 | 2.22 | 0.034 | 1.015 |
| ISO1600 素材 + ISO100 的 LUT | 5.13 | 5.82 | 5.32 | 0.103 | 1.073 |
| 换用「流传版」AWG3 矩阵 | 8.89 | 22.56 | 8.99 | 0.200 | 0.769 |

读法：
- **遗漏 Rec.709 OETF 逆**（把显示码值直接当线性光送进 LogC3 编码）：ΔE 均值 14.33，彩度 ×0.760
- **用 gamma 2.4 代替 OETF 逆**（常见的第二类错误：把 EOTF 当成 OETF 的逆）：ΔE 均值 5.95，彩度 ×1.110
- **跳过 Rec.709 → AWG3 基色变换**（直接以 709 数值冒充 AWG3）：ΔE 均值 8.00，彩度 ×1.116
- **三线性插值（33³）**（替代四面体插值）：ΔE 均值 0.22，彩度 ×1.003
- **65³ LUT + 四面体**（验证 LUT 尺寸是否够用）：ΔE 均值 0.17，彩度 ×1.000
- **解析式还原（不查表）**（把还原 LUT 换成 4096 点曲线，隔离 LUT 离散化误差）：ΔE 均值 0.09，彩度 ×0.999
- **输入 8-bit 量化**（10-bit 底线被破坏的情形）：ΔE 均值 0.35，彩度 ×0.997
- **还原 LUT 的 R/B 轴读反**（解析顺序写错时的真实后果）：ΔE 均值 20.77，彩度 ×0.934
- **ARRI LUT 的 R/B 轴读反**（同样错误在 3D Look LUT 上被放大）：ΔE 均值 21.64，彩度 ×0.968
- **用 v1 还原 LUT 处理 v2 素材**（两代曲线参数不同（机型分两包发布））：ΔE 均值 2.03，彩度 ×1.015
- **ISO1600 素材 + ISO100 的 LUT**（单条曲线覆盖所有 ISO 的残差）：ΔE 均值 5.13，彩度 ×1.073
- **换用「流传版」AWG3 矩阵**（矩阵来源未核实带来的饱和度漂移）：ΔE 均值 8.89，彩度 ×0.769


## 5. E3 量化与色阶断裂

| 指标（输出统一按 10-bit 计） | 10-bit 输入 | 8-bit 输入 |
|---|---|---|
| 未钳位的输入域（码值） | 70 … 575 （506 级） | 18 … 143 （126 级） |
| 底部/顶部平台（输出码值） | 1 / 995 | 1 / 995 |
| 不同输出码值数 | 482 | 126 |
| 平均输出步长（码值） | 2.06 | 7.93 |
| 拉伸倍数（输出跨度/输入级数） | 1.96 | 7.87 |
| 最大连续空档（码值） | 4 | 15 |
| 相邻输出码值最大 ΔE | 0.28 | 0.92 |
| 输出码值范围 | [2, 994] | [2, 993] |

这里有个反直觉的地方：管线把一个较窄的输入域**拉伸**到几乎满输出域（1.96×），所以 10-bit 输入几乎 1:1 落到输出（平均 2.06 码/级，最大空档 4 码）；但 8-bit 输入只有 126 级可拉，输出端平均步长变成 7.93 个 10-bit 码值、最大空档 15 码，相邻台阶 ΔE 0.92 —— 这是渐变天空上看得见的台阶。**8-bit 采集在这条管线里没有经济性**，与指导书 §5 的判断一致。

## 7. E5 LUT 采样精度

| 配置 | 对解析式 ΔE 均 | ΔE 最大 | 最大码值差 |
|---|---|---|---|
| 33³ 四面体 | 0.093 | 0.558 | 0.0117 |
| 33³ 三线性 | 0.249 | 0.932 | 0.0177 |
| 33³ 最近邻 | 4.316 | 9.497 | 0.1664 |
| 65³ 四面体 | 0.017 | 0.033 | 0.0004 |

33³ 查表相对解析曲线的码值误差：最大 0.0243、平均 0.0007。结论：33³ + 四面体已经够用（误差远低于 1 个 10-bit 码值）；三线性的误差在同一量级，但它是「轴对齐」插值，遇到大幅度色域映射的 Look LUT 会明显变差；最近邻完全不可用。

还有一条容易被忽略的：**33³ LUT 在 LogC3 顶端插值后到不了满量程**。本例输出峰值只到 0.9725，即 10-bit 码值 995/1023。原因是顶部格元跨过了陡峭的肩部，线性（含四面体）插值无法还原格元内部的拐点。这是网格尺寸的结构性问题：若要求纯白精确到 100%，只能加大 LUT 尺寸，或在 LUT 之后补一级标量增益。如果发现「白总差一点」，先查这里，别去动 LUT。

## 9. 三条硬边界（比调参更重要）

### 9.1 第三方 App 拿不到 Magic-Log

荣耀的 Magic-Log 是**相机 App 内部的视频模式**，Camera2 暴露给第三方的是 RAW / YUV 流，不包含那条厂商 Log 曲线。所以「录制 Magic-Log → 实时映射」在第三方 App 里**无法成立**：你录到的是 RAW 或 P010，而不是 Magic-Log。

可行的产品形态只有两条：

1. **文件处理型**：用户用原生相机录 Magic-Log，App 导入视频 → 解码 → 本管线 → 重新编码。（这是本仓库管线能直接复用的地方，也是精度承诺唯一成立的地方。）

2. **RAW 自建 Log**：Camera2 取 RAW10/12，自己做去马赛克、白平衡、黑电平，然后**直接编码为 LogC3**（跳过荣耀 LUT，因为根本用不上）。这条路没有任何厂商 LUT 依赖，数学上更干净，但要自己解决 RAW 视频的帧率与热问题（多数机型 RAW 连拍 < 10fps）。

### 9.2 宽容度损失

顶部 5.8 档高光在第一步（还原 LUT 输出 709）就被压缩，属于路线选择带来的固定代价，见 §6。

### 9.3 精度天花板

本报告能证明的是「实现正确」。真实精度取决于三件本仓库**不包含**的东西：荣耀官方还原 LUT、真实 Magic-Log 素材、ARRI LUT。三者到位前，任何 ΔE 数字都不代表 ARRI 保真度。


## 10. 到 Android 的移植对照

| 阶段 | Python | GLSL (`glsl/logc3_pipeline.frag`) |
|---|---|---|
| 还原 LUT 采样 | `LUT3D.sample(x, 'tetrahedral')` | `sampleLut3D(uRestoreLut, …)` |
| OETF 逆 | `transfers.rec709_oetf_inverse` | `rec709OetfInverse` |
| 709→AWG3 | `matrix_709_to_awg3()`（float32 matmul） | `uM709ToAwg3 * linear709` |
| LogC3 编码 | `transfers.logc3_encode` | `logc3Encode`（`log2(x)*0.30103`，ES 3.0 无 `log10`） |
| Look LUT 采样 | `LUT3D.sample` | `sampleLut3D(uLookLut, …)` |

纹理约定：`data[r,g,b,3]` 与 `texelFetch(lut, ivec3(r,g,b))` 一一对应，上传时 `GL_RGB16F` + `glTexImage3D(..., N,N,N, GL_RGB, GL_FLOAT, data)` 即可，不需要在 CPU 侧做转置。`glsl_mirror.py` 与 numpy 管线的逐像素最大偏差 **3.6e-7**（即 float32 的 1~2 ULP），回归测试见 `tests/test_pipeline.py::test_glsl_mirror_equivalence`。

上真机后仍需验证：`highp` 精度限定符是否被驱动降级、`GL_RGB16F` 过滤是否硬件支持、以及 `log2` 在驱动端的 ULP。这三项 CPU 侧测不出来。


## 11. 拿到真实素材后的验证顺序

1. `python -m magicrri info --lut <官方还原LUT>` 确认 size / DOMAIN_MIN / DOMAIN_MAX / 是否 1D。
2. `python -m magicrri probe --lut <官方还原LUT>` 用 0..1023 灰阶楔确认输出单调、并给出真实有效域（哪个输入码值处开始有输出、哪个码值处到顶）。
3. 拍灰卡（多 ISO）确认黑电平：还原 LUT 输出的最暗块应落在 0 附近且三通道一致。
4. 再跑色卡 ΔE。先看 ΔL* 再看 ΔC*：ΔL 系统性偏差通常来自解码曲线选错，ΔC 系统性偏高通常来自漏掉色域矩阵。
5. 最后才动 Look LUT。
